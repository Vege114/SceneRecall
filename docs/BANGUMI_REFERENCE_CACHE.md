# Bangumi 参考图分批缓存

Bangumi 图像缓存用于补齐本地匹配参考。来源图片和新下载图片仍是候选，缓存不会自动确认角色身份，也不会改变已有人工确认或撤销决定。

## 使用方式

在角色确认界面或视听身份界面主动点击「缓存 Bangumi 参考图」。系统按来源角色关系优先处理主角，其次配角，再处理其他角色；该顺序不推断角色是否在当前视频出现。

已有完整且内容哈希一致的本地图会直接复用，不占本批下载额度。每次界面请求最多尝试下载 20 张，单批总时限为 60 秒。还有未处理图片时返回下一批游标；角色确认界面显示「继续缓存 Bangumi 参考图」，视听身份界面再次点击缓存按钮也会携带该游标。

角色确认界面报告来源有图、本地已缓存、主角缓存、剩余待缓存、角色总数及撤销来源图的数量；视听身份界面在本批处理结果中补充主角缓存和剩余数量。缓存统计表示图片状态，不是识别覆盖或角色出场率。单张下载失败会记录原因，仍能继续后面的角色；一轮结束后可重新从第一批补齐失败项。

## 完整性与状态

- 缓存命中须检查文件存在、大小有效且 SHA256 与图库记录一致。
- 文件缺失或损坏时会重新下载；若内容与原图库项相同，恢复原文件并保留参考 ID、人工确认状态和审计记录。
- 已撤销的来源图继续保持撤销。默认补齐不会使其重新成为有效参考，也不会因旧撤销图存在而遮蔽同角色的有效新图。
- 缓存开始、写入和完成阶段检查作品范围与图片来源。角色名单、来源 URL 或批次模式改变后，旧游标失效，须从第一批重新开始。

## API

`POST /api/assets/{asset_id}/references/cache-bangumi` 接受：

```json
{"max_images": 20, "cursor": "上次响应中的 next_cursor", "refresh": false}
```

首次请求省略 `cursor`。`max_images` 是 1–20 的整数，接口默认值为 12；`cursor` 是服务器返回的 24 位十六进制值，不应自行构造。`refresh` 默认为 `false`，补齐模式跳过完整缓存；显式设置 `true` 才检查完整来源 URL 是否返回了更新图片。刷新模式与补齐模式不能混用同一游标。发现不同内容时新增候选，不自动撤销或替换已有人工确认。

响应保留 `imported`、`existing`、`skipped`、`errors` 和 `references`，并增加 `attempted`、`next_cursor`、`time_limited` 与 `coverage`。`coverage` 包含全部角色、来源有图、完整缓存、撤销、剩余及主角相关统计。`next_cursor` 为空表示本轮扫描结束，不保证所有下载成功；应同时检查错误和剩余数量。

## 实现与验证范围

实现位于 `backend/scenerecall/bangumi_reference_cache.py`，路由在 `backend/scenerecall/visual_identity_api.py`。本功能不读取或生成知识库内容，也不控制普通人物裁剪的 PNG 保留策略。

`tests/test_bangumi_reference_cache.py` 包含主角优先、49 角色分批覆盖、失败项后续补齐、完整缓存复用、损坏修复、游标失效、撤销状态与超时续批用例；`frontend/tests/character_confirmation.test.tsx` 包含游标请求和覆盖提示用例。本文记录实现行为与测试范围，不声称本轮完成了真实 Bangumi 网络下载或识别效果验收。
