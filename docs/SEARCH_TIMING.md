# 搜索耗时记录

搜索结果下方的「搜索总耗时与阶段记录」展示本次前端与后端的实际计时，并可下载 JSON。计时不改变查询、排序、缓存或模型选择，不会因打开诊断而调用模型。记录仅包含随机请求 ID、查询字符数、类型、筛选数量、返回数量、阶段时长、操作次数、数据量和缓存状态；不保存查询原文、角色名、路径、凭据或图片。记录随当前结果保留在页面内存，用户可主动导出。

## 测量边界

| 记录 | 实际边界 |
| --- | --- |
| 点击到结果 DOM 可用 | 指针点击搜索按钮产生的 `click` 事件时间戳，到 React 提交本次结果 DOM。时间戳统一到浏览器 performance 时钟；不兼容时退回点击处理函数入口，并以 `click_time_source` 标明。包含点击事件分发到表单提交的时间，不包含按下指针到松开生成 click 的时间，也不含缩略图加载。键盘激活和程序提交使用 `trigger=form_submit`，不伪造点击指标。 |
| 点击到表单提交／绘制机会 | `click_to_submit_ms` 补足原提交计时之前的区间；`click_to_paint_opportunity_ms` 到两次 requestAnimationFrame 的机会点。前台页面可减少浏览器节流，但仍不证明图片已加载或像素实际显示。 |
| 提交到结果 DOM 可用 | 浏览器的表单提交处理函数进入，到 React 提交本次结果 DOM。包括组装请求、请求等待、解析和界面提交；不含用户输入过程、事件进入处理函数之前的等待或缩略图加载。当前没有查询输入防抖，`debounce_ms=0`。 |
| 提交到绘制机会 | 提交到两次 `requestAnimationFrame` 后的机会点；不是画面已实际显示或图片加载完毕的保证。后台标签页的回调可能延迟。 |
| 前端准备请求 | 提交处理函数进入到调用 `fetch`。包含组装与序列化请求、同步页面状态更新。 |
| 请求发起到响应头 | `fetch` 调用到其 Promise 返回响应。包含浏览器调度、连接与传输、未单独测得的服务入站等待以及后端处理。 |
| 响应头到 JSON 已解析 | 收取响应体、JSON 解析及 JavaScript 调度。不能将其全部解释为下载速度。 |
| 后端应用总时长 | 搜索计时中间件入口到响应头可交付；包含会话检查、路由、搜索、来源核对、JSON 序列化。操作系统、ASGI 接收前或事件循环进入该中间件之前的等待无法单独区分。 |
| 请求到 JSON 的剩余项 | 前端请求到 JSON 的持续时间减去后端应用持续时间；包含传输、未测入站等待、响应体、解析与调度，不能称为「纯网络」。这里只比较持续时间，不跨前后端时钟相减时间戳。 |
| 浏览器资源计时 | 浏览器能提供本次完整 `PerformanceResourceTiming` 时，单独列出请求前准备、请求到首字节、响应体传输；未提供时明确留空，不填零。首字节时间包含服务端处理。 |

## 后端阶段

`X-Search-Request-ID` 关联请求；`X-Search-Timing` 返回 `search-timing-v1` JSON；`Server-Timing` 返回后端应用总时长。前端 API 读取最终响应头，获得包含 `response.json` 的完整记录。JSON 正文本身继续保持原搜索协议。无需读取进程全局「最后一次查询」来取得记录，因此同时搜索的阶段不会串到另一条请求上。

每个 span 包含 `id`、`parent_id`、`name`、相对请求起点的 `start_ms` / `end_ms`、`elapsed_ms` 和实际状态。所有后端偏移使用同一进程的单调时钟，线程中的记录也使用同一时钟。父阶段包含子阶段，四路召回并行，**不要把子阶段与父阶段相加，也不要把四路召回直接相加当成总时长**。比较区间可识别重叠；顶层区间之外的空白仍是未进一步拆分的应用调度／准备开销。

- `snapshot.*`：取得与验证索引、作品资料和编码器版本；`.work` 是实际执行线程内的区间。
- `query.character_names`：按检索范围解析角色姓名、简称和别名；`query.character_names.revision` 核对名录版本。状态只记录命中数量、是否展开等信息，不含姓名或查询原文。
- `recall.parallel` 与 `recall.lexical/semantic/visual/concept`：完整并行召回墙钟以及各路召回区间。未配置分支仍显示短区间及零候选。
- `lexical.sql_tokenize.work`：SQLite 字面检索、分词及结果读取。
- `semantic.*`：文字语义索引快照、实际查询编码及索引读取排序。没有文字语义模型时不会伪造编码阶段。
- `visual.model_identity` / `encoder.identity.work`：本地图文模型文件身份与运行依赖核对。身份核对可命中本进程内部文件哈希缓存，该区间不等同模型加载。
- `visual.query_cache_lookup`：磁盘查询向量缓存命中状态。命中时不出现 `visual.query_encode`。
- `encoder.prepare_and_wait`：编码器请求线程开始到启动／复用进程之前，包括请求锁与本地模型资源等待、读取设置、核对模型身份；这些部分未单独拆分，不能把整个区间称为纯排队。`visual.query_encode` 到 `encoder.request.work` 之间还包括异步线程调度。
- `encoder.worker_start` / `encoder.worker_exchange`：实际启动或复用进程，以及向编码进程发送请求到收到结果。`worker_model_load_ms` 只在这次启动了新进程时引用 worker 测得的模型加载持续时间，热进程记零；`worker_inference_ms` 来自这次 worker 编码。worker 持续时间只作区间内说明，不把其时钟偏移放入父进程时间线。
- `visual.matrix_cache`：矩阵命中、是否实际构建与流式回退。`fallback_reason` 区分 `cache_disabled`（缓存预算为零）、`retained_budget_exceeded`（保守留存估算超过字节预算）、`allocation_error`（确实捕获 Python `MemoryError`）、`builder_declined`（其他构建器明确返回空，原因未细分）。`memoized_fallback=true` 表示复用该索引版本与范围先前记下的回退结果，本次未重建；它不会把上次预算回退改称内存分配失败。`cache_budget_bytes` 是本次上限；存在时 `attempted_retained_bytes` 是构建器最后已计算的保守估算，`retained_bytes_phase` 指明记录元数据或向量阶段，并非系统实测 RSS 或完整索引的最终内存量。`visual.matrix_build.work` 是确实发生的索引解码与矩阵构建；`visual.matrix_score`、`visual.top_results` 分别计相似度计算、排序与结果读取。现有重试会全部保留在时间线内，`snapshot_retries` 是实际重试次数，父级总时长包括这些尝试。
- `results.*`：各路合并排序、可选模型重排、展示去重与选择、可选解释生成。禁用模型重排时该区间标明 `enabled=false`。
- `canonical.source_records` / `.work`：读取当前原始证据，父区间包含线程调度；`canonical.enrich` 核对与补齐来源、播放定位和展示字段。
- `visual_verification`：只有主动启用候选视觉复核时出现。
- `response.json`：实际 JSONResponse 序列化，包含响应字节数。

编码器计时通过独立适配器实现，原 `visual_encoder.py` 与 worker 的实现指纹保持不变。增加计时不会使已有视觉向量、磁盘查询缓存和任务快照失效；实际权重、预处理或编码实现变化仍按原规则隔离。

## 来源重建与版本核验的细分

`snapshot.acquire` / `snapshot.validate` 的 `phase` 标明本次核验的用途，`pass` 从 1 起按请求内实际核验顺序递增。普通检索的三次核验分别为：

| phase | 发生位置 |
| --- | --- |
| `initial` | 召回前取得索引与资料快照。 |
| `after_recall` | 召回后确认版本未变化。 |
| `after_canonical` | 重建、补齐最新来源后再次确认版本。 |

启用查询理解、重排或解释时还可能出现 `interpreted`、`interpretation_fallback`、`interpretation_source`、`planning_source`、`before_rerank`、`before_compose` 等用途；发生重试时次数也可能增加。不能把所有记录强行归成固定三次。每次核验内部可继续区分：

- `snapshot.revision.sqlite`、`.knowledge`、`.encoder`：索引版本、作品资料版本、编码器文件版本。
- `knowledge.scopes`、`knowledge.projection`：确定资料范围、重建已审核的作品资料投影。后者包含来源文件读取、原文哈希、解码与投影组装。
- `knowledge.revision.runtime`、`.identity`、`.baseline`：知识运行时状态、角色身份资料文件版本、基础资料版本；`knowledge.baseline.snapshot` 是基础资料快照读取。
- `character.snapshot`：角色名录快照与缓存；`query.character_names.revision` 保留对名录版本核验的外层计时。

`selected_assets` 记录当前搜索筛选实际选中的素材数；`knowledge.revision.identity` 的 `scope_assets` 记录身份版本核验涉及的作品范围。**单集搜索仍可能核验整个作品的身份资料**，应按这两项实测数量解释耗时，不能假定所有核验都只访问一集。各阶段还保留作品范围数、资料卡片数、原文数、路径数量、缓存命中／未命中／逐出次数等数值状态。

`canonical.owner_lookup` 先定位候选所属素材，记录候选数、去重后的请求记录 ID 数及来源素材数。随后每个 `canonical.asset_records` 用请求内的 `owner_index` 区分素材，不输出素材路径或 ID：`produced_count` 是重建出的整素材记录数，`produced_visual_count` 等是类型分布；`requested_record_count` 是其中落入候选 `id`、`member_ids`、`source_ids` 集合的记录条数，**不是最终展示结果条数**。两者用于判断实际请求的记录相对整素材重建规模有多大。

来源内部再分为 `records.asset_metadata`、`.annotations`、`.observations`、`.scenes`、`.audio`、`.retrieval`、`.subtitles`；`records.observation_filter`、`.assemble`、`.work_projection`、`.subtitle_compact` 分别记录筛选、组装、补充作品字段与字幕合并前后的数量。`retrieval.load_validate` 记录窗口及观察／身份附属记录数。`identity.decorate`、`identity.resolver_init`、`identity.resolve_batch` 分别衡量身份字段补充、解析资料初始化、批量解析，并保留记录、实体、参考图等数量。

## 文件与校验操作汇总

`search-timing-v1` 兼容增加可选的顶层 `operations`。前端将其展示在默认折叠的「文件与校验操作汇总」中；旧记录没有该字段时仍正常显示。每个操作包含 `count` 和 `elapsed_ms`，以及存在时的 `identity_calls`、`unique_count`、`repeated_count`、`identity_limit_reached` 与输入字节数等数值状态。

这是**整个请求的操作累计**，每次实际底层调用只计一次，不通过父阶段逐层重复累计。每个操作同时归到最近的活动 span，其 `attributes` 包含 `{操作名}_count`、`{操作名}_ms`、`{操作名}_unique_count` 等局部统计；父 span 不自动继承子 span 的这些数值。诊断用数值计数器也只归到最近 span。不要再把顶层操作累计与各 span 的局部累计相加。

| 操作 | 边界与解释 |
| --- | --- |
| `fs_exists`、`file_stat`、`file_glob` | 文件存在性、文件元信息和目录匹配。 |
| `file_read_text`、`json_parse` | 文本读取（**包含解码**）与 JSON 解析分开；JSONL 一次解析操作可以产生多条记录，以 `jsonl_record_count` 辅助解释，`json_text_chars` 是字符数，不是字节数。 |
| `digest_serialize`、`digest_sha256` | 哈希输入序列化（包含 UTF-8 编码）与实际 SHA-256 分开，`digest_bytes` 是哈希输入字节。 |
| `source_read`、`source_sha256`、`source_decode` | 知识来源原文读取、完整性哈希和解码分开，各自附输入字节数。 |
| `file_read_bytes`、`reference_sha256`、`projection_sha256` | 原始字节读取、角色参考图哈希、作品资料投影哈希。 |
| `scope_view`、`knowledge_cache_*`、`character_profile_load`、`character_names_build` | 作品范围读取、资料缓存装载／转换／大小估算、角色档案装载与姓名表构建。 |
| `record_copy`、`identity_merge` | 记录复制与身份字段合并。 |
| `lock_wait`、`library_lock_wait`、`knowledge_cache_lock_wait`、`character_cache_lock_wait` | 只计获取锁的等待，不含持锁期间工作。 |

操作耗时可能嵌套或并行，且已包含在阶段时长内；**各行不能全加总，也不是额外开销**。读取调用受操作系统文件缓存、解码、Python 调度等影响，不能直接称为纯磁盘 I/O 或磁盘读取速度。

资源身份仅在本次请求内用于去重，不输出路径、原文、哈希值或其他身份内容。`identity_calls` 是提供了资源身份的操作调用数，`unique_count` 与 `repeated_count` 分别表示第一次遇见与重复遇见的身份；没有身份的操作不伪造唯一数。请求总计与各 span 分别去重，因此各 span 的唯一数不能相加当作请求唯一数。每类操作的去重集合最多保留 32,768 个身份；达到上限后设置 `identity_limit_reached=true`，次数和耗时仍继续累计，但唯一数与重复数已不足以完整划分所有调用。重复计数表示重复访问，不表示命中应用缓存或重复访问可以安全跳过。

计时通过请求上下文传播到执行线程，同一请求的并行工作共享受锁保护的统计；不同请求使用独立上下文和聚合对象。没有活动搜索计时时，底层操作不创建全局累计，也不通过全局缓存计数的前后差值推断本次命中情况。

### 阈值展示模式

搜索页默认 `min_match_score=50`（2026-11-04 调整，历史实验曾用 75），使用严格大于比较，并按相对匹配度降序显示全部符合条件的候选；重复片段仍按现有证据规则合并。普通查询的相对匹配度为完整召回集合中该记录的 RRF 融合分除以本次最高 RRF 分，再乘以 100，口径为 `relative_rrf_v1`。有明确人物目标的阈值查询先按命中帧人物证据对非视觉贡献加权，再除以完整集合的原始 RRF 最高分，口径为 `character_grounded_rrf_v1`，因此最高有效分也可能低于 100%。具体公式和权威来源复核见[人物计分说明](SEARCH_CHARACTER_PRIORITY_20261104.md)。

分数随查询、检索范围与可用召回分支变化，**不是正确概率，也不是模型原始余弦相似度**；没有足够证据的候选仍保持“部分匹配”。原始 `score` 继续保留，阈值模式另用 `match_score`。现存索引的完整候选分布与使用边界见[阈值曲线说明](SEARCH_THRESHOLD_20261104.md)。

阈值模式取消本地影片候选的前 10/50 条限制，词法概念与知识卡片也不再按前 5/50 项预截断；视觉仍要求正相似度，文字语义仍保留原有有效距离条件。LightRAG 实验分支自身仍有限定的检索数量，会在诊断中明确说明。可选模型只核对原有预算内的一小批候选，未核对的候选不会因此消失；模型分数与统一阈值分分别保存。可选解释最多覆盖前 10 个，并明确其覆盖范围，不裁掉列表结果。

响应 `selection` 保存本次实际应用的阈值、分数口径、融合候选数量与来源核验后的实际返回数量。改变页面输入不会改写上一轮结果的阈值说明。未传 `min_match_score` 的旧 API 调用仍兼容原有 `limit` 参数。

比较阈值模式与旧耗时记录时，需要同时记录返回数量、涉及素材数、缓存状态和是否刚重启。原 12 集、仅返回 10 个结果的 63.8902 秒样本见 `search-detail-full-warm-timing-20261103.json`；增加返回结果可能扩大来源重建范围，不能把新模式首次构建矩阵的耗时当成同条件暖缓存对比。

先等待分析、索引和后台准备任务完成，记录代码提交、库大小、模型／硬件和是否仍有任务运行。分别选择台词、画面和角色查询，每种记录第一次与多次重复请求，保存请求 ID 和导出的 JSON。查询家族由测试者标注，程序不通过语言猜测「角色查询」。

首次请求不必然是冷模型：启动准备可能已预热模型，磁盘查询向量缓存也可能来自之前的会话。按 `query_cache_hit`、`matrix_cache_hit`、`matrix_built`、`worker_started` 等实际状态描述每条；不要为了制造冷状态随意删除共享缓存。若已确认没有运行任务而重启服务，应注明重启只清除进程内状态，不清除磁盘缓存；首次进程内矩阵构建和首次模型加载也可能出现在不同请求。真实测试结果另随本轮验证文档记录，不用早期人工观察的宽泛秒数区间推断瓶颈或宣称提速。
