# v0.2 implementation contract

Internal records and REST use snake_case. Time is integer milliseconds relative to asset start. Source data are versioned JSON; all indexes disposable. Engineering tests use generated fixtures and provider doubles. Real media/model validation is recorded separately in `VALIDATION.md` and is not inferred from synthetic tests.

## Per-stage execution choices (2026-10-13)

`AnalysisInput.execution` contains `transcript`, `preparation`, and `subtitle`, each `serial|parallel`, plus strict positive integer `max_concurrency`, with no application-defined operational upper bound. Fresh application/GUI defaults are parallel/16. New connection `max_concurrency` defaults to 16 and is also a strict positive integer without an application-defined ceiling. Persisted user defaults, task snapshots and explicit connector settings remain unchanged. Browser inputs require an exactly representable positive integer; zero, fractions, non-finite values and unsafe JavaScript integers are rejected before submission. Request-model defaults and missing persisted choices remain serial; the serial request's unused count remains 3 to preserve legacy batch fingerprints, and its actual width is always one. Settings persist defaults; each submitted analysis/batch item freezes its own full choices, and changing choices invalidates GUI estimates. Character reanalysis accepts optional execution choices, inheriting current settings only when omitted. Deepening, deep sub-batches, context refresh, character publication and the global episode queue remain sequential.

The analysis/batch and scene-character-reanalysis startup forms offer an unchecked `设为默认值` checkbox. When selected, Start first submits `PUT /api/settings` with only `defaults.execution.max_concurrency` and modes for currently visible stages, then enqueues the task. Nested settings merge preserves hidden modes, bindings, sampling/crop/budget defaults and other settings. Estimate, closing a modal, unchecked Start and toggling the checkbox alone do not save defaults; checkbox state is excluded from estimate identity. Save errors abort enqueueing. If settings save succeeds but enqueueing fails, the UI refreshes settings and reports the partial outcome; if enqueueing succeeds but refresh fails, the task remains submitted and is not created again. Successful creation refreshes bootstrap so the next task uses saved defaults. These startup overrides do not change connection caps. Serial-only deepening/legacy reanalysis forms omit the execution-default checkbox.

The global `模型与设置 → 执行与并发` section owns the task default cap, the three stage modes and each connection cap. It also shows bound connections and the resulting stage cap (`min(task, connection)` for parallel stages, one for serial stages); actual dispatch still depends on remaining units and cumulative budget admission. Connection editing and the sampling/budget analysis-default form omit duplicate concurrency controls. `PUT /api/concurrency` accepts `{execution?:partial_ExecutionOptions,profiles?:{[profile_id]:positive_integer}}` and returns `{settings,provider_profiles}`. Omitted execution fields and unlisted connection caps are retained. It validates the complete request and preserves unrelated settings, model fields, timeouts, prices and secret storage. Before publishing settings and profiles, it durably writes a replayable journal; the journal is cleared only after both files are published, and failed/interrupted publication is recovered before later reads/writes or startup use. A response must not report successful save before both publications finish. Existing profile and settings APIs remain compatible, and settings consumers read current persisted defaults rather than a stale startup snapshot. Changing defaults does not rewrite queued/failed task execution snapshots; connection caps remain live at execution time.

Official source review (2026-10-13): [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documents `agents.max_concurrent_threads_per_session` for spawned subagent threads within one session. SceneRecall launches isolated `codex exec` requests with `agents.enabled=false`; that setting is not a ceiling on its independent CLI processes. The reviewed official [usage documentation](https://learn.chatgpt.com/docs/pricing) does not establish a universal maximum independent CLI concurrency. Do not label a default or undocumented server behavior as a known Codex maximum. User-selected concurrency remains subject to actual workload, budget admission, account allowance and service capacity; no paid stress test or unlimited-capacity claim is made.

Effective stage width is bounded by both task and current connection limits. Each connection uses one shared in-flight counter across cap changes and all capabilities, rather than separate pools keyed by cap. Raising the cap wakes queued callers; lowering it lets submitted calls finish and blocks new admission until the remaining count fits the new cap. Parallel transcript batches share frozen prior memory and bounded preceding original cues; parallel visual batches share frozen prior memory plus original boundary frames, without consuming sibling inferred results by completion order. Serial modes retain rolling batch memory. Results are assembled chronologically and retain evidence coverage and cross-batch adjacent-scene merging. Model inputs identify the independent context, and receipt identities include canonical inputs, preventing reuse across changed reasoning dependencies while permitting equivalent paid outputs to be reused.

Each paid call reserves up to three attempts and its estimated cost in a durable call-keyed map before dispatch. Budget admission and additive accounting are serialized under the library lock; all active reservations count against request/fee limits. Successful receipts are persisted before accounting. Recovery accounts all completed receipts exactly once before conservatively charging unresolved reservations; legacy single-call reservations remain compatible. Bounded workers stop admitting new work after pause/cancel/budget exhaustion/error, drain already admitted calls and preserve their receipts before reporting termination. Service shutdown owns and drains its workers. OCR only activates a full subtitle track when all batches succeed; retry reuses completed batches.

Public analysis jobs expose `execution`, `stages`, and `analysis_strategy`; internal in-flight call maps and receipt paths are omitted. Missing old job choices project to serial. Batch idempotency omits default serial execution to preserve existing request fingerprints; meaningful choice changes are distinguished. `stage_metrics[stage].wall_elapsed_ms` measures stage wall time for the latest execution; `elapsed_ms` retains cumulative provider-call durations, including retries. These statistics do not establish real recognition accuracy or provider throughput. `stage_progress` retains its existing shape and is rebuilt on resume.

## Per-task Codex model selection (2026-10-13)

Analysis, batch analysis items, character reanalysis and scene deepening accept optional `model_overrides` keyed by active `preparation`, `vision` or `subtitle` stage. Each entry identifies `provider_type: "codex_cli"` and the bound `profile_id`, with optional `model` and `reasoning_effort`. Omitted model inherits the connection; empty model requests the CLI built-in default. Missing/null reasoning effort uses the model default. Wrong stages, changed binding IDs and API-provider overrides are rejected before enqueueing. API per-task model selection is deferred.

Persist source connection snapshots separately from effective task snapshots. Calls use effective snapshots in request-local scope; task choices never rewrite provider settings or leak between simultaneous calls. Connection identity checks compare the original source snapshot. Resume/retry preserve the frozen choices. Explicit reasoning effort participates in recognition/scene receipt cache identities; absent effort preserves legacy cache identities. CLI invocation passes selected model via `--model` and effort via a bounded `model_reasoning_effort` configuration argument while retaining existing isolation.

Public job responses expose only `task_models:{stage:{provider_type,profile_id,model,reasoning_effort}}`, not private connection snapshots. Runtime timeout/concurrency settings remain live so failed tasks can recover after a connection repair. Batch idempotency distinguishes omitted model from explicitly empty model. An active deepening task with different effective model choices cannot be silently reused. Character reanalysis uses the configured analysis strategy consistently for estimation and creation, including explicit legacy strategies.

`GET /api/codex/models` requires the normal local session and returns model IDs/names, supported efforts and default efforts from the local CLI model metadata cache, plus source/freshness information. It does not run inference or read credentials. Missing/invalid caches return a usable empty catalog with explanatory text; consumers retain inherited/default options. Catalog entries do not guarantee current account entitlement. The UI clears incompatible effort selections and invalidates estimates after changes; each participating Codex stage can use an independent model/effort, including stages sharing one connection.

## Subtitle-guided scene analysis (2026-10-13)

The GUI submits `analysis_strategy=scene-chunks-v1` for new vision jobs. `preparation` and `vision` must both be bound; they may share one profile if that profile declares both capabilities. Preparation requires text and image input and supports OpenAI-compatible API and Codex CLI connections. A direct API request that omits the strategy selects scene chunks when preparation is bound, otherwise content keyframes. Explicit `content-keyframes-v1` and persisted older jobs retain their original strategy/checkpoints; adding a binding does not convert an existing task. Local keyframe selection and global worker concurrency are unchanged.

The sequence is selected subtitle OCR, transcript preparation, visual partition, then chronological deeper understanding. OCR completes first when requested; otherwise current external/container/OCR cues are used immediately. Transcript preparation references original cue IDs and preserves overlapping/bilingual cues. Its input batches are bounded to 100 cues and 24 KB. New scene tasks persist internal `config.visual_batch_size`: at most 24 new frames for a Codex CLI preparation profile or 56 for an API profile. Legacy tasks without the field retain 56, preserving original input units and paid receipt identities. Visual preparation inspects every selected frame in chronological batches with up to eight preceding reference frames, rendered as numbered/timecoded contact sheets of up to 16 pictures each. References provide boundary context and cannot be cited as new current-frame evidence. A continued first chunk can merge with the preceding adjacent chunk; nonadjacent similar scenes retain distinct ranges. A static picture may cover more cues than fit in one request: local cue context is bounded to 100 sampled cues/16 KB plus bounded transcript summaries, while every original cue remains stored and searchable.

After an issued `prepare_visual` request fails with `code=timeout` or exhausts valid output attempts with `code=invalid_output`, scene execution can bisect the frozen input near its midpoint. Each child must contain at least seven new frames; a split must fall between strictly increasing `at_ms` values so same-timestamp frames stay together. A leaf without a legal split reports the provider error. Codex CLI visual output validation gets one attempt before fallback rather than repeating the same large input up to three times; other Codex stages and API transport/output retry policies retain their existing behavior. Authentication, allowance, ordinary network/protocol failures and preflight errors do not initiate splitting, and `request_count=0` never does. The right child receives up to eight preceding original frames as boundary context. Children retain the original frozen story/character inputs and only original sampled cues and transcript references overlapping their local range.

Each child owns its normal frozen input, durable reservation, result receipt and usage accounting. Before any child admission, `scene-splits/<parent_receipt_key>.json` stores the split decision; recovery follows it without reissuing the failed parent, reuses completed children, and checks controls/budgets before each remaining sequential child admission. Sibling children do not expand stage or connection concurrency. The joined partition is validated against all original frame IDs, cue IDs and time bounds; valid adjacent continuation can merge, while a merge that would exceed schema limits retains both valid chunks and their facts. The aggregate parent receipt has zero requests/usage/cost and does not charge child work again. Failed-parent attempts and all additional child requests count against cumulative budgets; insufficient budget pauses work with successful children retained. User `timeout_s` remains unchanged.

Optional `scene_key` is a normalized visual-environment candidate label (at most 120 characters), never a verified place/person/event identity. After adjacent continuation merges, each chunk links to at most 16 temporally nearest nonadjacent candidates with the same nonempty key in the same video/partition, returned chronologically in `related_chunk_ids`; their separate ranges and evidence remain unchanged. These bounded links need not be reciprocal. Every chunk retains its key for future broader lookup. Deep upgrades preserve these navigation fields. The UI calls them “可能相似的场景”, initially shows six links and can reveal more; a link opens the target time and scene even beyond the first records page. Links are not fact evidence or proof of narrative continuity.

Scene partition validation requires exact, ordered coverage of selected new frames, valid time/shot/frame/cue references, and at most eight representative frames including each chunk's first and last retained frame. The complete partition is atomically activated before deep analysis, replacing covered legacy/current boundaries together; a partially overlapping replacement is rejected. Search indexing applies changed/retired records incrementally rather than rewriting an episode after each chunk. Complex chunks are deepened within the same sequential run. After an earlier chunk is deepened, subsequent simple chunks receive a bounded text-only `context_refresh` through preparation so their continuous understanding uses that result without another image upload.

Automatic deep analysis uses original representative frames plus provider-selected important-change frames in `deep_frame_ids`; missing/empty choices from legacy responses conservatively fall back to all retained frames. Manual deepening and explicit character reanalysis read every retained chunk frame. Sub-batches contain at most 24 current originals for API profiles or 12 for Codex CLI, plus at most eight character reference images. All original keyframes remain stored; selected important changes are split into sub-batches rather than truncated to a single request. Character IDs resolved in completed sub-batches are supplied to later sub-batches before the final scene is published; persisted partial results and deterministic entity identities support crash recovery. Automatic appearances retain model confidence, and initial scenes do not prematurely remove legacy character evidence before a covering deep result exists.

`SceneStore` saves immutable versions under `assets/<asset_id>/analyses/<run_id>/scenes/`, with active references in `active-analysis.json`. A scene contains stable `id=chunk_id`, `start_ms,end_ms,shot_ids,frame_ids,representative_frame_ids,deep_frame_ids,subtitle_ids,summary,understanding_level=initial|deep,needs_deep,reason,visual_facts,dialogue_facts,inferences,memory_before,memory_after,dependencies,provenance`. Visual facts are `{text,frame_ids}`; dialogue facts are `{text,cue_ids}`; inferences may cite both and remain explicitly labeled as inference. Fact references must belong to that scene; cue intervals must overlap its time range. Historical character pictures, memory or dialogue cannot establish a current visible action. IDs derive from the asset and scene boundaries; upgrading a chunk preserves its ID and boundaries. A new partition with different boundaries creates different IDs and preserves historical files.

Memory inputs contain bounded prior summaries, recent scene state, unresolved references and relevant character dossiers; they do not grow with the full transcript/history. Recent story context is limited to 18 KB; character context is separately bounded, with at most 16 relevant dossiers/eight pictures. Same-episode chunks advance in order. Cross-episode context requires the same project and known season/episode numbers, includes only earlier episodes with complete valid coverage, and records missing episodes or incomplete/stale coverage as gaps. Unnumbered videos do not infer narrative order. Provenance records source chunk identities and revision digests. Visual facts, dialogue facts and uncertain inferences remain separate throughout.

Frozen stage inputs, successful call receipts and deep partial results live in `scene-inputs/`, `scene-receipts/` and `scene-deep/`; visual fallback decisions live in `scene-splits/`. Cache identity includes video fingerprint, keyframe plan, effective subtitle text/version, model identity, prompt versions, provider-specific `deep_batch_size`, persisted `visual_batch_size` when present, manual character revision, project membership revision, semantic annotations and input memory. Missing `visual_batch_size` preserves the legacy dependency digest. Inputs/outputs and usage receipts are persisted before advancing; retry replays completed results and idempotently accounts their usage. Failure stops the dependent sequence instead of skipping a predecessor. An activated initial scene that still has `needs_deep=true` remains searchable, but contributes a `pending_deep_analysis` gap rather than usable prior memory. A new same-episode later-range job checks all preceding active chunks, beyond the bounded memory gap list, and refuses work while any preceding chunk still needs deep analysis; retry or manual deepening of the unfinished chunk itself remains allowed. A prior episode containing such a gap is not treated as complete and contributes no cross-episode summaries until its required deep analysis succeeds. Changed inputs invalidate an old job before another model call/publication; changing the deep batch policy also invalidates the saved dependency snapshot. Deep result provenance records `deep_batch_size` and `deep_analyzed_frame_ids`. Automatic deepening reconciles following simple scenes in the same run; manual deepening or semantic edits mark dependent later records `context_stale` with `stale_reasons` and never automatically launch an episode/series rerun. Favorites and notes alone do not change semantic cache identity.

`POST /api/assets/{asset_id}/chunks/{chunk_id}/deepen/estimate` accepts `{max_requests=1000,max_cost=null}` and returns an estimate without calling a model. `POST` to the same path without `/estimate` creates a persistent analysis job; equivalent active work for that chunk/version is deduplicated. It requires the vision binding, preserved original frames and currently accessible original media, but does not require preparation. Budgets are cumulative across retries; normal provider calls reserve up to three attempts. Codex monetary budgets are rejected while request budgets remain available. Search itself never starts preparation, OCR, vision or deepening; the UI opens a budget dialog and creates work only after explicit confirmation.

Scene search results use `kind=scene`, stable chunk IDs, understanding level and stale badges. Scene records participate in collections, Markdown/JSON citation export and backup/restore. Upgrade switches only that chunk's active version and preserves annotations/favorites/history. Backups include frozen inputs, receipts and partial results; these can contain local frame paths but never credentials. Restore validates original frame/cue references and memory source identities, including historical versions. Asset detail initially displays at most eight representative originals and reveals other retained frames in pages of 24; search cue links open the exact subtitle/time even beyond the initially visible subtitle page.

Estimates add `estimated_requests_min,estimated_requests_max,cost_estimate_min,cost_estimate_max` and `stage_estimates` entries with `requests_min,requests_max` for `subtitle,transcript,preparation,vision,context_refresh`. Preparation uses the persisted batch size: its lower count is the number of original visual batches, and its upper count includes every node in the reachable binary fallback tree under the seven-frame and timestamp rules. Deep/context refresh counts are ranges until partitioning determines the chunks; these are not guaranteed runtime counts and transport/output retries can add requests beyond the tree estimate. `cost_estimate` remains the lower estimate for compatibility and unknown prices/CLI keep monetary values unknown. Job `stage_metrics` maps stages to `request_count,elapsed_ms,cache_hits,usage`; local `keyframes` and `index` timing is separate from model stages. The UI labels `transcript` as 台词整理, `preparation` as 视觉分块, `deep_analysis` as 深入理解 and `context_refresh` as 更新连续理解. Performance acceptance is a measured ≥50% reduction in model-stage time on the same material/configuration, with plot/dialogue/character/pure-visual retrieval checks; fewer requests or synthetic success alone cannot establish it.

Job `stage_progress` is optional and only added by the scene execution path. It contains `transcript,preparation,deep_analysis,context_refresh`, each with `{completed:number,total:number|null,status:pending|running|completed}`. Transcript and preparation count completed input batches; visual fallback children contribute usage but the original preparation batch completes only after all children are joined and validated. Deep analysis counts original-image sub-batches using the actual selected frame set and provider-specific batch size; context refresh counts simple scenes requiring text reconciliation. Before partitioning, deep/context totals are `null` and pending, displayed as “待分块确定”. A known zero-work stage is `0/0` and completed, including transcript/preparation/context refresh in a manual-deepening job. Stages become running when execution starts and completed when their count reaches the known total. Paused/failed jobs can retain a running stage status; overall `job.status` explains the interruption. Each execution resets these absolute progress counters and reconstructs completion by replaying receipts, saved parts or finished targets, so resume does not accumulate duplicate progress. Progress is separate from cumulative request/time/cache/usage accounting and never enters model input, cache identity or immutable scene versions. The GUI combines supplied progress with metrics; legacy jobs without this field keep their existing metric display without inferred stage states.

## Projects, folders and migration (2026-10-13)

`Library.organization` is an `OrganizationStore`. `organization/catalog.json` stores `organization_version=1`, stable projects, folders, per-asset membership and historical character mappings. Projects have `id,name,kind,folder_id,tags`; folders have `id,name,parent_id`. A video belongs to zero or one project. Folder ancestry cannot contain cycles. Folder deletion reparents direct children/projects; project deletion unassigns member videos without deleting source data. Existing `work_id` and immutable observations are unchanged.

`GET/POST /api/projects`, `PATCH/DELETE /api/projects/{id}`, `GET/POST /api/folders`, `PATCH/DELETE /api/folders/{id}` manage organization. `POST /api/projects/assign` accepts `{asset_ids,project_id}` (null unassigns). Project responses include `asset_count`. Asset projections include `project_id,project_name,folder_id,folder_ids,tags,membership_revision,character_scope_id`. Search supports `project_id`, `folder_id` (descendants included), and `tag` alongside existing filters.

First migration groups legacy assets by normalized kind/series and preserves their original cast scopes. New project scopes are stable across renames. Moving assets maps historical `(scope,character_id)` into the destination registry, copying relevant human fields and respecting redirects/tombstones. Exact source identity can be reused; names alone never merge identities. Source registries remain archived. Current reference pictures and appearances must belong to current members. Organization and registry changes publish through a durable after-image journal; startup rolls it forward before serving requests. Running vision work in either affected scope blocks reassignment; queued/paused jobs become stale. New vision snapshots include membership revision and cannot resume after reassignment.

Backup includes organization and historical identity maps. Restore validates the complete graph, upgrades legacy backups in staging, merges nonconflicting organization records, and rejects conflicting identities without overwriting them. A durable restore journal is written before any asset publication; startup completes interrupted file publication before organization migration, retaining staging until completion. Keyframe plans validate frame references, ranges and precise timestamps; incomplete plans need a new local scan because runtime jobs are not backed up.

## Deletion, source files and restoration

Video cards, asset detail and bulk selection support deletion. Projects/folders retain their default non-cascading behavior: deleting a project unassigns its videos; deleting a folder reparents its immediate contents. `delete_contents=true` also removes the selected project's videos, or the entire selected folder subtree including projects and videos. All application-data deletions are retained in a persistent recycle bin. Deleted videos are excluded from active library/search/favorites, model reference pictures and ordinary asset/frame/plan access; their evidence remains available for restoration and backup validation.

`POST /api/deletions/preview` accepts `{kind:assets|project|folder,asset_ids?,id?,delete_contents=false,delete_source=false}`. It returns `token,title,asset_count,project_count,folder_count,assets:[{id,title}],projects:[{id,name}],folders:[{id,name}],blocked_jobs,source_files,source_file_count,delete_source,source_files_preserved`. Deletion responses expose source paths only in this authenticated preview; public trash entries omit them. The token binds the confirmation to the selected scope and source state.

`DELETE /api/assets/{id}?expected_token=...&delete_source=false` deletes one asset; `POST /api/assets/delete` accepts `{asset_ids,expected_token?,delete_source=false}`. `DELETE /api/projects/{id}` and `DELETE /api/folders/{id}` accept `delete_contents`, `delete_source` and `expected_token` query parameters. The UI always sends its current preview token and refreshes the preview when the deletion mode changes. Responses contain `{trash,deleted_asset_ids,deleted_project_ids,deleted_folder_ids}`. Running work blocks unsafe deletion; stale queued work cannot recreate deleted videos or resume against a changed membership.

`delete_source=false` leaves original media untouched. With `delete_source=true`, source deletion is permanent, requires `expected_token`, and is explicitly confirmed separately from application-data deletion. Preflight checks the registered file identity/content and rejects missing, changed, unsafe or shared sources before modifying application data. After preflight, the application deletion and per-source pending intents are durably stored before unlinking each source. Long content checks run outside the library lock; immediately before unlink, current sharing and file identity are rechecked under that lock. `trash.source_results` records `pending|deleted|error` and the affected asset IDs; partial source failures remain visible and are never reported as complete success. Interrupted pending operations become uncertain errors and are never automatically replayed. A later file at the same pathname is not permission to delete it. Original external subtitle files are not removed.

`GET /api/trash` lists deletion groups with `id,kind,title,deleted_at,asset_count,project_count,folder_count,assets,projects,folders,delete_contents,delete_source,source_results`. `POST /api/trash/{id}/restore` returns `{restored,restored_asset_ids,restored_project_ids,restored_folder_ids}`. Restoring application data does not regenerate permanently deleted source media or automatically restart old tasks. Stable identities and retained analysis/annotations are preserved; conflicting changes are rejected without overwriting current data.

## Local selection and durable batches

`POST /api/local-files/list` accepts `{path?,kind:video|subtitle,offset=0,limit=200}` and returns `{directory,parent,entries:[{name,path,type:directory|file}],next_offset,total}`. It lists immediate children, naturally sorted, with pagination; hidden entries and non-regular/unreadable files are omitted. Paths are normalized; this is an authenticated backend-host selector, not an arbitrary file-content endpoint. No videos are uploaded by selection.

`POST /api/imports` accepts `{request_id,project_id?,items:[{item_id,...AssetInput}]}` and returns a persistent import Job. Top-level project assignment, when present, applies to every item. Public `items` contain `item_id,name,status,asset_id?,error?`, where status is pending/running/completed/existing/failed. Each file commits independently; duplicates return the existing asset without moving it. `GET /api/imports/{id}` returns `{job,items,project_id}` with authenticated input configurations for editing (common project or null). Paths remain absent from ordinary job summaries and backups. `POST /api/imports/{id}/retry` accepts `{items:[corrected item inputs]}` for unsuccessful items only. If the asset was already published before a progress/index failure, only the original configuration may be retried; changing that item cannot relabel an already imported video.

Animation import items may additionally select `anime_profile:{mode:"bangumi",subject_id:positiveInteger}` or `{mode:"scratch"}`. The GUI automatically searches by animation project name or standalone work title, reads a unique exact match, asks the user to select ambiguous candidates, and gates unresolved animation imports until a subject/link or scratch mode is selected. Existing direct API inputs remain compatible. `POST /api/bangumi/search {query}` returns `{status:"matches"|"not_found"|"error",candidates,error?}`; `POST /api/bangumi/subject {reference}` accepts a positive ID or known-host subject URL and returns `{source:"bangumi",subject,characters,fetched_at,warnings}`. All reads require the existing local session and use pinned local bgm-cli JSON output; no movie/subtitle content or personal Bangumi credentials is passed to it.

The server fetches/caches dossiers before publishing import jobs, persists immutable per-item source snapshots privately in task configuration, and omits them from public editable inputs. Replay uses the original request identity before network access; retries retain saved archive selections/snapshots, while legacy unsuccessful imports can choose an initial archive. Source archive and seeded cast publish together through the existing organization transaction. Projects and projected assets expose `anime_profile:{mode:"bangumi",dossier}` or `{mode:"scratch"}`. `POST /api/projects/{id}/anime-profile` and `POST /api/assets/{id}/anime-profile` accept only the minimal selection, read server-owned source data, and supplement existing animation archives. Same-subject refresh fills missing metadata and appends roles; different bound subjects are rejected.

Seeded cast IDs retain `external_source` and external identity bindings; initial profiles appear in bounded model text context even at zero appearances. Work summaries and biographies are prior references, never current visual evidence. Remote portrait URLs are UI references; model image context still uses local observed frames. Human fields, merges/deletions, and old evidence survive additive seeding and archive moves. Moving to an unbound animation project inherits the source archive and unobserved cast; same external identities reuse destination decisions, incompatible subject bindings reject before writes, and detachment preserves the archive. Backups retain source snapshots, casts, and catalog bindings.

Batch submission idempotency uses request ID plus payload digest in SQLite; same ID/different content returns 409. Each import item also stores its stable `import_item_key` with the atomically published asset so a crash before progress persistence cannot import it twice. Failed items do not stop later files. Import and local subtitle extraction never call providers.

`POST /api/jobs/batch/estimate` accepts `{items:[AnalysisInput]}` and returns per-asset estimates plus summed frames/requests/cost and warnings. Any unknown member cost makes the total unknown. `POST /api/jobs/batch` accepts `{request_id,items:[AnalysisInput]}` and atomically returns `{batch_id,jobs}` in project/season/episode order. Budgets remain per episode; successful outputs and cumulative usage remain on each job. `POST /api/jobs/batches/{batch_id}/{pause|resume|cancel|retry}` controls eligible members and returns `{jobs,failures}`. Duplicate analysis submissions cannot create another group.

## Content keyframe plans

Both scene-chunk and legacy content analysis reuse `content-keyframes-v1` local plans. A single low-resolution decoding pass detects cuts and combines five-pose local comparison, near-duplicate collapse, held-pose preference (80 ms), visual novelty and sharpness. [PySceneDetect ContentDetector](https://www.scenedetect.com/docs/latest/api/detectors.html#contentdetector) continues to detect cuts from adjacent-frame color/intensity changes; representative selection is a separate content scoring step. Continuous motion uses content changes, not periodic sampling. Every detected shot has at least one usable representative. This selects representative finished-video pictures, not codec I-frames or guaranteed original animation drawings. OCR remains independent.

`POST /api/keyframe-plans` accepts `{asset_id,start_ms=0,end_ms?}` and returns a reusable plan with `id/plan_id,job_id,status`; `GET /api/keyframe-plans/{id}` adds progress and, when complete, frames with preview URLs plus shots/batches/frame_count/batch_count. Scanning is a persistent `keyframe_scan` job without model configuration or model calls. Same fingerprint/range/algorithm reuses a completed plan. Cancelled/failed scans can be retried; completed plan publication is atomic. Decoder cancellation joins worker threads and reaps FFmpeg. Interrupted local scans may restart.

`media.scan_keyframes(path,start_ms,end_ms,checkpoint=None,progress=None)` returns `{algorithm,algorithm_parameters,shots,frames,batches}`. The algorithm's thresholds and feature settings are stored with the plan, not exposed as user tuning controls. Frames preserve relative `pts,time_base`, original `source_pts,source_time_base`, rounded `at_ms`, `shot_id` and `reason`. `media.extract_keyframes(path,frames,out_paths,checkpoint=None)` matches precise source PTS, verifies actual decoded timestamps and never silently substitutes the next frame. Extraction is bounded to 256 pictures per call; workflow preparation uses chunks of 128. The FFmpeg `select` filter combines exact-PTS predicates with a balanced addition tree, keeping expression depth logarithmic instead of creating a left-associative chain that can exceed FFmpeg's parser depth limit before decoding emits any frame. Dense 128- and 256-picture batches must retain the same timestamp verification and output ordering as smaller batches. The local frame resolver uses a per-operation registry snapshot for plan validation/reuse, scene frame loading and backup restoration, avoiding one full registry read per picture. Every ID, confined path and existing file is still checked; snapshots are not cached across operations, and timestamp validation remains unchanged.

Legacy content analysis sends at most eight chronological selected frames per model batch, never crosses a shot, and has content-derived contiguous coverage boundaries. Scene analysis reuses the selected frames, not these old request boundaries; plan `batch_count` is not its model request estimate. Coverage is not a claim of observing every intervening instant. Persisted plans live at `assets/<id>/keyframe-plans/<plan_id>.json`, and previews use the existing registered evidence-frame route. Cache identity includes plan, algorithm and exact selected timestamps; provenance records the selection.

`AnalysisInput.keyframe_plan_id` is optional for creation, required for a vision estimate: `/jobs/estimate` only reads completed matching plans. A direct new `/jobs` request without a plan performs local content scanning before any model request. Deprecated `window_ms/frames_per_window` are accepted but ignored by new vision tasks; estimates and created jobs return deprecation warnings. Stored pre-upgrade jobs without a strategy remain `uniform-v1`, with original checkpoints and an explicit UI label. Character reanalysis accepts `keyframe_plan_ids:{asset_id:plan_id}` and follows the same new-task rule.

## Container subtitle extraction

`media.subtitle_tracks(metadata)` reports all subtitle streams using the global stream `index`, `codec`, `language`, `title`, `default`, `forced`, `supported` and an optional unsupported reason. `media.extract_subtitle_track(source,stream_index,output,metadata=None)` returns the actual extracted path (ASS/SSA -> `.ass`, other supported text -> `.srt`). Times in this extraction are relative to the same playback origin as `media.probe.start_time_ms`. `subtitles.parse_container_subtitles(path,duration_ms,offset_ms=0)` preserves text and language groups, skips drawing/comment/empty events, and records any boundary clipping for review. External subtitle parsing remains strict.

`POST /api/media/subtitle-tracks` accepts `{video_path}` and returns `{tracks,recommended_stream_index,duration_ms}`. `GET /api/assets/{id}/subtitle-tracks` returns the same for a registered, available source. `POST /api/assets/{id}/subtitles/extract` accepts `{subtitle_stream_index?,subtitle_offset_ms=0}` to extract or switch a container track on an existing OCR/container asset and refresh lexical search. All routes require the normal local session; no providers or automatic embeddings are invoked.

Auto import chooses a supported text track deterministically by default disposition, non-forced disposition and global index; an explicit index must identify a supported subtitle stream. No tracks resolves to legacy `embedded` with a fallback explanation, deferring OCR model configuration until analysis. Bitmap-only or failed text extraction raises an error, never silently calls OCR. The legacy `embedded` mode still means burned-in frame text; it does not render soft bitmap subtitles. `external` remains the user's supplied file. OCR jobs are refused for extracted text, including older jobs queued before conversion.

Each successful extraction stores its source file, `analyses/<run_id>/subtitles.jsonl`, run metadata, and an atomic `active-analysis.json.container_subtitles` pointer. Cues carry `source=container`, source stream index/codec/language/title, offset, asset and run identity. Only the selected container track is projected into detail/search; old OCR and container runs and annotations remain available as history. Existing collections, backup/restore and offline reading retain these records. Re-extracting the same track with unchanged content/timing keeps stable cue identity.
